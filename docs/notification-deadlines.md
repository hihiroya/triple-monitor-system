# 通信と通知の時間上限

Tourismの長時間停止に対する防御として、既存の共通HTTP取得とDiscord通知に有限の時間上限を設ける。2026年10月6日の実行で通知成功10件の後にログが途絶えた原因、および10月5日の停止原因を特定したものではない。

- 1要求の20秒はヘッダー取得から本文読了までの合計。本文を読み終えたResponseを呼び出し元へ返し、status・headers・redirect metadataを維持する。RSS、公開HTML、X、Notion、Discordの既存利用経路に共通適用する。
- Discordは1項目の通知全体を90秒以内とし、要求ごとの期限を20秒と残り総時間の小さい方にする。timeoutはAbortControllerで進行中の通信を中止し、要求・総期限・待機タイマーとabort listenerを解放する。
- 429は初回を含め最大3試行、累積待機30秒まで。Retry-Afterは秒数とHTTP日時を扱い、欠落・不正値は従来どおり1秒。指定待機が累積許容量を超えるか、総期限までに再送できない場合は、待機を短縮せず失敗させる。テスト用の待機短縮環境変数は使わない。
- 診断ログにはsource key、項目IDのSHA-256、試行番号、HTTPステータス、待機秒数・累積待機秒数、経過ミリ秒、処理段階と失敗理由を記録する。項目IDハッシュはstate内のIDから計算して照合できる。webhook URL、認証情報、通知本文、応答本文、通信例外の生文は記録しない。
- 通知成功は本文読了まで確認してから既存checkpointへ進む。後続通知が失敗しても先の成功済みcheckpointを保持し、失敗項目と未実行項目は既読にしない。通知先では受信済みでも応答確認が失敗した場合の重複可能性は残る。

テストはfake fetch・fake timersとローカルHTTPサーバーだけを用い、外部Discordへは送信しない。本文の停止、長いRetry-After、累積待機超過、再試行時の残り総時間、通信中止・タイマー解放、機密情報非出力、後続timeout時のディスク上checkpoint保持を検証する。既存の状態ブランチ連携テストも再実行する。

workflowのjob上限、依存、保護設定、既読の過去状態は変更しない。Tourism・Notionの再開、実通知、PRマージはこの変更には含めない。実サービスでの429・本文停止の再現、および実運用での期限動作は未検証。
